# Open Questions

This file tracks open questions for the project and records how past
questions were resolved. Add new questions at the top of the *Open* section;
when a question is answered, move it to *Resolved* with the decision and
date.

| Q19 | Do the unmaintained transitive Rust crates flagged by `cargo audit` need action? | `cargo audit` on `src-tauri/Cargo.lock` reports **0 vulnerabilities** and 17 warnings, none with a fix available at this project's level: 11 are the GTK3 stack (`gtk`, `gdk*`, `atk*`, `glib`, `proc-macro-error`), which `cargo tree --target aarch64-pc-windows-msvc` confirms is not part of the Windows dependency graph at all, and 6 are `unic-*` crates reaching us through `tauri-utils` → `urlpattern`. Nothing to fix here; revisit when Tauri drops `urlpattern`/`unic-*`, and re-evaluate the GTK warnings only if macOS/Linux builds ever happen (Q15). CI now runs this audit on every push/PR so a real vulnerability won't go unnoticed. | 2026-08-29 |
| Q18 | Should the SVG renderer move from `innerHTML` string concatenation to safe DOM element creation (`createElementNS`/`setAttribute`)? | Raised by CODEX-REVIEW.md. The actual vulnerability (unescaped attribute interpolation) is fixed — see CODEX-REVIEW-RESPONSE.md — by escaping every value at render time (`src/canvas/render.ts`, `src/connectors/routing.ts`, `src/core/text.ts`) plus validating colors/ids/imageSrc at the document-parse boundary (`src/model/serialization.ts`). Moving off `innerHTML` entirely would remove this whole *class* of risk structurally (no future call site could reintroduce it by forgetting to escape) at the cost of a much larger rendering-engine rewrite. Worth doing eventually; not required now that the underlying bug is closed and covered by regression tests. | 2026-07-08 |
| Q17 | Formal accessibility audit against brief §8.14? | Controls have ARIA labels, focus-visible styles, and keyboard shortcuts exist (§10 of INSTRUCTIONS.md), but no structured audit (screen reader pass, color-contrast check, color-blind-safe default palette) has been performed, matching CODEX-REVIEW.md's finding that this claim isn't yet backed by evidence. | 2026-07-08 |
| Q16 | Profile performance with 500–2,000 elements on real Windows ARM hardware per brief §8.15? | The renderer fully rebuilds SVG markup via `innerHTML` on every change (`src/canvas/view.ts`) and undo/redo uses full-document snapshots (`src/core/editor.ts`) — reasonable MVP choices, but unproven at the brief's target scale on actual ARM hardware (only functionally exercised via the Playwright smoke test with a handful of shapes). Now that a real Windows ARM build succeeds (see INSTALLATION.md), this can finally be tested directly. | 2026-07-08 |
| Q15 | Should FlowShark ship macOS and Linux desktop builds? | Currently only Windows (ARM64 + x64) is configured: `src-tauri/tauri.conf.json` only declares the `nsis` bundle target, icons are only generated as `.ico`/`.png` (no `.icns` for macOS), and `.github/workflows/ci.yml` only builds on `windows-11-arm`/`windows-latest` runners — matching the brief's stated scope (§3: Windows 11 ARM primary, Windows 11 x64 secondary; macOS/Linux were never requested). Nothing in the Rust shell (`src-tauri/src/lib.rs`) or the TypeScript app is Windows-specific, so adding `dmg`/`app` (macOS) and `deb`/`appimage` (Linux) bundle targets plus matching CI jobs would likely work with little to no code changes — but this is unverified since it's never been attempted or tested. | 2026-07-08 |

Revisit if: (a) the affected machine's security team confirms/denies a block event for that file, or (b) rollup ships a newer win32-arm64-msvc build and someone can confirm the native binary loads cleanly there. Until then, the WASM override is the safer default for Windows ARM contributors generally, since it produces an identical build (verified via the full test suite + smoke test) at a small build-time cost. | 2026-07-08 |
