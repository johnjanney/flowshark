| Q21 | Should the desktop build hold a *durable* filesystem permission for files outside Documents? | The static Tauri scope is `$DOCUMENT/**`; a file opened elsewhere through the dialog gets a session-only runtime grant, so its recent-files entry stops working after a restart. FlowShark now detects this and offers to reopen the file through the dialog (restoring access) instead of showing a raw permission error, and removes the entry if the user declines — so nothing silently breaks. A real fix needs persisted scopes/bookmarks: either widen the static scope (worse — it hands the renderer standing access to more of the disk), or persist runtime grants across launches. Revisit when Tauri's fs plugin offers a supported persisted-scope API. | 2026-08-29 |
| Q20 | Pin third-party GitHub Actions to commit SHAs and `cargo-audit` to a version? | `.github/workflows/ci.yml` references actions by mutable tag (`@v4`, `@stable`, `@v2`), so a compromised or retagged action would execute in the pipeline that builds and publishes installers. The fix is mechanical — `uses: owner/action@<sha> # vX.Y.Z` — but each SHA must be verified against the upstream repository, which the sandbox that raised this could not reach (github.com and crates.io are both blocked there), and an unverified pin is a hard CI failure. Workflow-level `permissions: contents: read` has been added in the meantime so the default token is least-privilege. Do the pinning from a machine with network access, then close this. | 2026-08-29 |
| Q19 | Do the unmaintained transitive Rust crates flagged by `cargo audit` need action? | `cargo audit` on `src-tauri/Cargo.lock` reports **0 vulnerabilities** and 17 warnings, none with a fix available at this project's level: 11 are the GTK3 stack (`gtk`, `gdk*`, `atk*`, `glib`, `proc-macro-error`), which `cargo tree --target aarch64-pc-windows-msvc` confirms is not part of the Windows dependency graph at all, and 6 are `unic-*` crates reaching us through `tauri-utils` → `urlpattern`. Nothing to fix here; revisit when Tauri drops `urlpattern`/`unic-*`, and re-evaluate the GTK warnings only if macOS/Linux builds ever happen (Q15). CI now runs this audit on every push/PR so a real vulnerability won't go unnoticed. | 2026-08-29 |
| Q18 | Should the SVG renderer move from `innerHTML` string concatenation to safe DOM element creation (`createElementNS`/`setAttribute`)? | Raised by CODEX-REVIEW.md. The actual vulnerability (unescaped attribute interpolation) is fixed — see CODEX-REVIEW-RESPONSE.md — by escaping every value at render time (`src/canvas/render.ts`, `src/connectors/routing.ts`, `src/core/text.ts`) plus validating colors/ids/imageSrc at the document-parse boundary (`src/model/serialization.ts`). Moving off `innerHTML` entirely would remove this whole *class* of risk structurally (no future call site could reintroduce it by forgetting to escape) at the cost of a much larger rendering-engine rewrite. Worth doing eventually; not required now that the underlying bug is closed and covered by regression tests. | 2026-07-08 |

| Q16 | Profile performance with 500–2,000 elements on real Windows ARM hardware per brief §8.15? | **Now half-answered.** `scripts/bench.mjs` is a reproducible benchmark (fixture generator + timings for parse, routing, SVG build, DOM commit, undo snapshot, drag frame, export) and README records an x64 Chromium baseline: at 500 elements a drag frame costs 23 ms median / 75 ms p95, so the brief's minimum target is met with limited headroom; by 2,000 elements it is 89 ms (≈11 fps) and unacceptable.
